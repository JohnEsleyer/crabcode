Architecture & Storage Blueprint

Data Storage, Runtime & Dependencies

A complete breakdown of where CrabCode persists data, its underlying runtime engines, directory structures, and dependency management mechanics.

📁 System & Project Storage Folders

CrabCode isolates global settings and scratchpads from project-specific virtual databases.

~/.crabcode/ (Default System Root — all data lives here)
├── settings.json (Root & environment paths)
├── crabcode.db (Global SQLite: Notes & Sandboxes)
├── templates/ (Dynamic IaC .yaml template files)
│ ├── python.yaml, go.yaml, rust.yaml
│ └── sql.yaml, surrealdb.yaml, javascript.yaml
├── sandboxes/ (Persisted sandbox files on disk)
│ └── <sandbox_id>/
│ ├── config.yaml
│ ├── main.py
│ └── ...
├── environments/ (Universal package toolchains)
├── temp_sandboxes/ (Extracted runtime execution folder)
│ └── <sandbox_id>/
└── playground/ (Global code scratchpads)
├── scratch.py, scratch.js, scratch.go
└── scratch.rs, scratch.sql, scratch.dart

<YourProjectFolder>/ (Workspace Root — stays 100% clean)
(No .crab/ folder — all sandbox data stays in ~/.crabcode/)

🎯 Custom Root Directory Bootstrap

You can move the CrabCode system data folder to an external drive or custom path via Settings.

// Bootstrap file location:
~/.crabcode_root.txt

// How CrabCode resolves the storage root at runtime (app.go):
1. Check if ~/.crabcode_root.txt exists.
2. Read custom path string from file.
3. If empty or missing, fallback to ~/.crabcode
4. Ensure universal env dir exists: <RootPath>/environments

// When saving a new custom path in Settings:
1. If old root exists and differs from new root,
   entire ~/.crabcode directory is COPIED to
   the new location via copyDir().
2. Old root is removed after successful copy.
3. ~/.crabcode_root.txt is updated.
4. Global DB connection is re-initialized at new path.

💾 SQLite Database Schema (/crabcode.db)

CrabCode uses embedded pure Go SQLite (modernc.org/sqlite) without CGO dependencies. The database is stored centrally inside your system base location (~/.crabcode/crabcode.db), not inside the workspace folder — keeping your project source tree 100% clean.

⚡ Application Runtime Stack

CrabCode runs as a native cross-platform desktop binary with multi-threaded Go process management.

Wails v2 Desktop Bridge Go 1.21 Backend Svelte 5 UI modernc.org/sqlite (Pure Go)
  • Go Backend: Manages file system operations, SQLite connection lifecycle, and asynchronous command execution loops.
  • IaC Execution Engine: The RunSandbox method parses the declarative YAML and executes a 4-phase lifecycle: Setup (env preparation) → Extract (virtual files to disk) → Build (compilation) → Run (execution with env vars).
  • Dynamic Template Scanner: GetTemplates() reads all .yaml files from <CrabRoot>/templates/ at runtime. No hardcoded template registry.
  • Process Streaming: Processes (os/exec) stdout/stderr pipes line-by-line and emits Wails runtime events (terminal_output) to the UI console in real time.

📦 Dependency & Toolchain Management

How CrabCode handles execution dependencies across workspace files and sandboxes:

  • Host Toolchain Integration: CrabCode executes runners directly using host binaries (e.g. python3, node, go, rustc, sqlite3, java, dart, g++).
  • Universal Env Directory: Stored inside <CrabRoot>/environments for isolated toolchains or local package caches.
  • IaC Setup Phase: The setup block in a sandbox YAML runs steps inside <CrabRoot>/environments/<name>/ before execution.
  • Dynamic Templates: All sandbox templates live as .yaml files under <CrabRoot>/templates/. New templates are detected at runtime — no recompilation needed.
